## 一、P0 必须修正

### P0-1（W4）列表同名元素定位全线失效，补 "容器锚点" 定位与坐标护栏

**定位**：方案第五章 W4「四级定位链」。

**问题**：

W4 定位链对 EasyBow 最高频的业务场景 ——**列表 / 表格行操作**—— 几乎全线失效。以聚水潭订单列表、淘宝订单列表为例，每一行都有「查看 / 编辑 / 详情 / 下单」，role 与 accessible name 完全相同：



* ②`role + accessible name 唯一匹配`：同名元素几十个，**唯一性永不成立**；

* ③`text + tag 匹配 + 中心点最近`：列表排序、新订单插入顶部、懒加载图片撑高后，"中心点最近" 的可能是**另一行**—— 点错行且无任何报错；

* ④`快照 rect 坐标兜底`：reflow 后坐标漂移，同样点错行。

此外，④坐标兜底 "页面未滚动时直接点" 护栏不足：窗口缩放、固定头 / 横幅插入、图片懒加载撑高布局都发生在 "未滚动" 前提下；而 W10 是**事后**核验，错误点击若已触发删除 / 提交 / 支付则不可逆。

虚拟列表（antd Table virtual、react-window 等）场景更严重：滚动后 DOM 节点被回收，①path 与④坐标**双失效**，只有语义定位可用。

**修正要求**：



1. **新增一级 "容器锚点" 定位（建议置于②之后、③之前）**：

* extract 时为每个候选记录最近稳定容器（`tr` / 卡片 / `fieldset` / 列表项）的**锚文本**（同行订单号、卡片标题、分组 legend）；

* 重定位时用 `role + name` 与祖先容器锚文本联合消歧：


  * Playwright 思路：`locator.filter({ hasText: '订单号' })`；

  * CSS：`tr:has(td:text("订单号")) button[aria-label="查看"]`（`:has()` 现已被主流 Chromium 支持）；

  * XPath：`//tr[contains(.,'订单号')]//button[.='查看']`（ancestor 轴）。

1. **④坐标兜底增加命中护栏**：点击前用 `document.elementFromPoint(x, y)` 校验最上层元素的 tag/text 与目标一致，不一致则放弃坐标法、回退视觉通道或升级。

2. **写操作禁用裸坐标**：目标动作属于提交 / 保存 / 删除 / 支付 / 下单类时，坐标兜底直接禁用（或强制人工确认），只允许语义级定位。

3. **快照 state 时效性**：disabled/checked 等 state 是快照时刻值，执行时以实时属性再判一次，避免依据过期 state 误判。

4. **W11 fixture 增补**：同名按钮长列表、排序后列表、虚拟列表、懒加载 reflow 四类用例（与 P2-1 合并实施）。

**验收影响**：



* W4 验收 "破坏测试页重定位 ≥90%" 必须包含**列表行操作用例**（现文案只提 "插入节点 / 复制同名按钮"，不足以覆盖）；

* 新增：列表排序 / 插入新行后，对指定锚文本行的操作正确率 ≥95%（写操作 100% 不允许错行，错行即失败）。

### P0-2（W1）智能等待缺自适应熔断，特殊页面会比现在更慢

**定位**：方案第四章 W1「DOM 稳定探测」及第十章风险表第一行。

**问题**：

现状 `waitSettle`（`executor.ts:435-446`）固定等待 600/1200ms。新方案改为 "距最近 mutation ≥ 250ms 才返回，总上限 8s"。对持续变动页面 —— 倒计时、轮播广告、骨架屏闪烁、WebSocket 通知、首屏 hydration——mutation 永不静默，会**每步吃满 8s 上限**：30 步任务最坏比现在慢约 13 倍。风险表仅写 "卡到 8s 上限变慢"，缓解措施（过滤样式类 mutation）不足以覆盖全部场景，且**没有回退机制**。

另发现两个设计缺口：



1. **首屏 hydration 未区分**：React/Vue 首屏 hydration 期间 mutation 洪峰是正常且必然的，用动作后的静默策略等首屏会稳定吃上限；

2. **mutation 分类口径 W1/W10 打架**：W1 想忽略 "纯样式 / 属性"mutation，而 W10 恰恰依赖 `aria-checked`、`disabled`、`value`、`aria-busy` 等**语义属性变化**判断勾选 / 启用是否成功。两份过滤逻辑若各写各的，会出现 "勾选了 checkbox 却报告页面无变化"。

**修正要求**：



1. **自适应熔断（必做）**：同一任务连续 2 次吃满 settle 上限 → 该任务后续自动回退到固定等待策略（沿用现 600/1200ms），telemetry 记录熔断事件与页面特征；提供 `smartWait` 手动关闭开关（已有规划，保留）。

2. **首屏 / 动作后分策略**：

* 首屏导航：以 `Page.loadEventFired` /isLoading 结束 + 固定窗口为准，不套用 mutation 静默；

* mutation 静默只用于**动作批之后**。

1. **统一 mutation 分类表（W1 与 W10 共用一份常量）**：

* 忽略：`style`、class 中的动画类、纯展示节点增删（轮播 / 广告容器，可按选择器黑名单）；

* 保留：`aria-*`、`disabled`、`checked`、`selected`、`value`、`hidden`、`role` 变化与结构性子节点增删。

1. **删除 "保底 120ms"**（或仅保留在慢速模式作为拟人下限）—— 页面已稳定时仍固定等 120ms 与 -30% 目标直接冲突。

2. **慢速模式等待公式写明确**，消除方案中 "保留固定节奏" 与 "信号提前退出" 的表述矛盾：

   `实际等待 = max(拟人下限, min(信号等待, 上限))`。

3. W11 fixture 增补 "持续动画页" 作为熔断验收页（见 P2-1）。

**验收影响**：



* 新增：持续动画 fixture 上，第 3 步起必须触发熔断回退，单步等待 ≤ 现状值；

* 基准任务 -30% 的统计需同时给出 P50 与 P90，防止均值下降、长尾恶化。

### P0-3（W1）"网络静默" 现有代码支撑不了，wait\_for network 有漏判

**定位**：方案第四章 W1 第 2、3 点；涉及 `cdp.ts:440-494`。

**问题（已核实源码）**：



1. 现有 netHandler **只监听&#x20;**`Network.responseReceived`（`cdp.ts:452-466`），没有 `requestWillBeSent` / `loadingFinished` / `loadingFailed` 的配对，**算不出 "在飞请求数"**。方案中提交类点击后的 "网络静默 300ms" 无法靠现有 `findResponseBody` 实现，需要新增 in-flight 请求生命周期追踪。

2. `findResponseBody`（`cdp.ts:483-494`）是**翻历史缓冲**（反向 find）。wait\_for 若沿用 "查缓冲" 模式存在时序竞态：动作后模型决策期间，高流量页面（ERP 一个动作常伴随几十个埋点 / 静态请求）可能把目标请求冲出缓冲。正确语义是 " 注册一次性匹配器，等待**未来**出现的匹配响应 "。

3. **只等 "响应完成" 不判 status**：等到 403/500 也算等到，任务会带着失败继续。现有 netLog **已经记录了 status 字段**，判定零成本。

4. `target="_blank"`**&#x20;漏判**：提交点击若打开新标签页（ERP 的预览、支付页常见），旧页面网络立即静默、DOM 不变，提交等待瞬间误返回成功。

**修正要求**：



1. 新增 in-flight 追踪：维护 `请求发起数 - 结束数（finished/failed）`计数，"网络静默"= 在飞 XHR/Fetch 数为 0 持续 300ms；类型白名单沿用现有 `['XHR','Fetch','Document']`（天然排除 WebSocket、EventSource 与静态资源）；

2. wait\_for network 改为**未来监听模式**：动作批结束时注册 URL 匹配器（支持 method 可选），Promise 在匹配请求 `loadingFinished` 且 status 为 2xx 时 resolve；4xx/5xx 直接判该步失败并进入 W7 反思流程；超时按 `seconds` 参数；

3. 提交类点击的自动等待同时监听 `Target.targetCreated`—— 若点击打开了新标签，等待目标切换 / 新页 settle，而非在旧页等静默；

4. 环形缓冲 50 条仅用于事后断言（测试模式），不作为 wait\_for 的实现基础；响应体仍按需拉取、过期清理（沿用现状）。

**验收影响**：



* 新增 fixture：提交返回 500 的页面（应判失败并反思，不得继续）、提交打开新标签页的页面（应正确等待新页）；

* W1 第 3 点 "上限 5s" 在新增 target 场景应顺延为新页 settle 上限。

### P0-4（W9）失败后全切 planner 模型的设计不成立

**定位**：方案第六章 W9 第 2 点 "连续 2 步失败后该任务后续步骤自动切 planner 执行"。

**问题**：



1. **根因错配**：执行步失败的主因是定位失效、元素遮挡、验证码、页面改版，换更强的模型生成同样的动作原语并不能解决；

2. **粒度太粗**："后续步骤全部切换" 可能还有 20 步，planner 预设为更贵的 reasoner，token 必然爆炸，与验收指标 9（token 不升）直接冲突；

3. **无回落机制**：一次波动导致全程贵模型；

4. **延迟灾难**：deepseek-reasoner 等推理模型每步数秒思考，用于逐执行步会严重恶化 "丝滑" 体感，与 P0 目标自相矛盾。

**修正要求**：



1. **执行模型不自动升级**。强模型只用于三个决策点：

* 重规划（W8）；

* L2 节点复核；

* 当前卡住节点的**单次 "专家重试"**—— 仅下一次模型调用走 planner，成功后立即回落主模型；

1. 增加迟滞规则：若未来放开执行升级，需 "连续 3 步成功自动切回"；

2. 设置页预设建议改为：主模型 = 快速对话模型（执行），planner = 强推理模型（规划 / 复核 / 专家重试），并在 UI 注明 planner 不参与逐步执行；

3. token 统计分列（已有规划）保留，新增 "专家重试次数 / 任务" 埋点。

**验收影响**：



* 删除 "连续 2 步失败自动切换执行模型" 相关表述与验收；

* 新增：配置 planner 后，纯执行步调用 planner 的次数 = 专家重试次数（可计数、有上限，建议每任务 ≤3 次）。

### P0-5（W8）重规划的上下文继承与安全兜底缺失

**定位**：方案第六章 W8 设计第 2、3 点。

**问题**：



1. **已完成节点冻结在改道场景下会死锁**：重规划的典型触发恰恰是 "页面实际状态与计划不符"（人工提前操作、session 过期、上一步副作用与预期不同）。只替换 planIdx 之后的节点，会把一个已经失效的 "已完成登录 / 已进入页面" 前提永久保留；

2. **上下文继承未写明**：W7 的 tried 失败清单、W6 页面地图若不传入重规划 prompt，新计划会立刻重蹈覆辙；

3. **缺安全兜底**：重规划后任务 "跑完但跑错" 的概率显著升高（尤其写操作），现行 L2 复核若可被跳过或降级，错误结果会直接收尾；

4. 触发条件 "步数消耗过半但节点进度 <1/2" 依赖节点粒度，而节点大小不均（一个节点可能是 "填完 20 个字段"），比例信号失真。

**修正要求**：



1. 重规划输入中，已完成节点清单允许模型把节点标记为 \*\*「需验证 / 需重做」\*\*（附当前页面证据），而非一律冻结；规划 prompt 明确 "以当前页面真实状态为准，已完成步骤若已失效必须重做"；

2. 重规划 prompt **必须继承**：原任务、已完成 / 待验证节点、当前失败节点、失败归因、W7 tried 清单、W6 页面地图、当前快照摘要；

3. **安全兜底**：本任务发生过 ≥1 次重规划，则 done 时强制云端 L2 复核，不允许本地复核通过、不允许跳过；复核不通过按重规划失败处理；

4. 触发条件改为：**连续 N 步（建议 3）无任何节点推进**，或节点连续复核失败 2 次，或 done 被拦下且模型明确报告页面与预期不符；删除 / 弱化 "步数过半 + 进度 < 1/2" 比例条件；

5. 重规划上限 2 次保留；时间线明示保留；重规划调用走 planner 模型（与 P0-4 一致）。

**验收影响**：



* 指标 6"中途改道自愈 ≥60%" 改为：**自愈且结果经 L2 复核正确**的比例 ≥60%（仅跑完不算成功）；

* 新增用例：任务中途使登录态失效，验证 "已完成节点被重做" 而非卡死。

### P0-6（全局）验收指标内在矛盾、基线顺序自相矛盾

**定位**：方案第三章 "建议实施顺序调整"、第十一章验收汇总、文末实施顺序。

**问题**：



1. **指标 9（token / 任务不升）数学上不成立**：W4（AX 80→150 + state 行内展示）、W7（反思段）、W10（delta 摘要行）、W6（页面地图行）每一步都在向模型上下文追加 token，不可能 "不升"；

2. **W11 顺序两处矛盾**：第三章说 "W11 骨架提前到 P0 末尾"，文末说 "W11 骨架 → W1 → W2"。而 W1/W4 的验收（-30%、成功率不降）都依赖回归集，逻辑上 W11 骨架必须先行；

3. **基线测量没有排期**：多个指标写 "先测"，但 5\~6 周排期中没有留下采集基线的日历时间；

4. **W7 指标可被操纵**："重复失败 -50%" 若不把被执行前拦截的尝试计入，拦截策略上线后数字自然下降，不代表任务变好。

**修正要求**：



1. 指标 9 修订为：**"云端 token / 任务升幅 ≤10%，且 token / 成功步（完成一个任务的总 token ÷ 有效推进步数）不升"**；W4 设计中补充量化：150 上限下每步新增 token 估算、30 步任务累计估算，经实测回填；

2. 统一实施顺序（详见第 4 节）：**step 计时埋点合入主干 → 3\~5 个自然日真实任务基线采集 → W11 三任务骨架 → 才动 W1**；

3. W7 指标口径修订：统计 "每个未达成目标的无效尝试次数（含执行前拦截、含换通道尝试）"，前后对比；

4. 所有 "先测" 指标在 W11 骨架完成时一次性建立基线值，填入验收表后才允许关闭对应工作项。

**验收影响**：见附录 A 修订表。

## 二、P1 建议补强

### P1-7（W5）Shadow DOM 穿透的三个技术细节



1. **现成实现可复用**：`extractor.ts:607-618` 图片提取已实现 shadow root 栈递归（注释明确提到淘宝 / 天猫 web component），W5 直接复用同一遍历模式，不需从零编写；

2. **rect 不要手工累加 host 偏移**—— 方案中 "rect 换算同 iframe 累加祖先 shadow host 偏移" 是错误设计：shadow 内元素 `getBoundingClientRect()` 直接返回视口坐标，手工累加在 host 带 CSS `transform: scale/translate`（弹层动画极常见）时反而算错。**仅跨 iframe 需要坐标空间变换**；

3. **W1 探针必须覆盖 shadow root**：主文档的 MutationObserver **收不到 shadow 内部的 mutation**，每个穿透的 shadow root 都要安装探针，否则 shadow 页面 settle 永远误判；同理，若为定位向元素注入 `data-easybow-*` 句柄属性，探针必须过滤自身属性，避免自己触发自己；

4. 建议 path 编码原生支持 shadow boundary（如 `12>3#0>5`），否则 shadow 元素连首次点击都没有快速路径，永远走全文语义匹配。

### P1-8（W10）delta 核验按动作类型区分，否则误报泛滥



* **假阴性**（全零 delta 但动作成功）：勾选 checkbox / 开关（仅 aria-checked/class 变化）、hover 展开菜单（批末已关闭）、瞬时 toast（快照时已消失）、fill（输入值不进候选文本）；

* **假阳性**（delta 非零但与动作无关）：轮播切换、广告加载、通知推送；

* 修正：

1. delta 规则按动作类型分流：fill 类比对 value 探针；toggle 类比对语义属性（与 P0-2 共用分类表）；仅 "导航类 / 提交类 click + 全零" 给强提示，其余给弱提示或不报；

2. 结构信号优先于总数阈值：是否出现 `dialog/alert/新列表行`、URL / 标题变化，比 "候选数 ±30%" 可靠；±30% 阈值先 telemetry 采一周分布再定值；

3. 时序写明：delta 复用下一步开头 settle 后的 extract 快照，**不额外提取**，守住 "零额外 CDP 往返" 承诺。

### P1-9（W3）结构化输出的探测方式与 schema 适配



1. **不要拿真实任务请求做三级探测**：首次 400 浪费用户真实一步（且大请求体可能已计费）。改为会话建立时 1-token 预检，或读取 `/models` 能力表；探测结果按 provider+model 缓存、会话内粘滞；

2. OpenAI strict json\_schema 要求全部字段 required + `additionalProperties:false`，现有 25+ 动词的联合参数契约适配工作量不小（oneOf 各家兼容度差，或全字段 nullable），1\~1.5 人日偏乐观；

3. Anthropic 侧可用 **tool\_use + tool\_choice 强制调用**实现事实上的 schema 输出（与 prompt cache 兼容），不必 "保持现状"；

4. DeepSeek / 通义 / 智谱 /vLLM 等 OpenAI 兼容端点对 json\_schema 支持参差，是降级探测的重点覆盖对象；

5. 解析失败阈值 3→2 与 few-shot 注入保留。

### P1-10（W7）失败签名粒度与清单边界



1. `动作名 + 候选文本` 在列表页会误伤：A 行「查看」失败后，B 行「查看」被当重复方式拦截。签名必须包含**容器锚文本**（与 P0-1 的锚点同一套数据）；

2. 区分失败性质：**方式失败**（元素失效 / 未命中 → 禁止重复同一方式）与**业务失败**（提交后服务端报错 → 修正表单后应允许再次提交），后者不进 "禁止重复" 逻辑；

3. tried 清单设上限：每目标保留最近 3 条、全局条数封顶，统一放在 prompt 动态后缀区（见 P1-12）。

### P1-11（W2）并行化的 P90 风险与截图策略



1. extract（evaluate）、getBoxModel（强制 layout）、captureScreenshot 并行，在重页面可能互相拖慢；盒子查询并发 10→25 会产生集中 reflow，并可能与贝塞尔轨迹的 rAF 节奏抢占主线程。验收除 P50<800ms 外**必须同时卡 P90**；拟人输入动画期间错开盒子批量查询；

2. "出错步事后补高清" 无法还原点击瞬间（若已导航，拍到的是新页面）。对定位诊断更有价值的是零成本记录**点击坐标 + 目标 rect**，在时间线渲染命中叠加标记；高清截图降级为次要手段；

3. 渲染进程崩溃时 executed 不返回，smart 模式该步会无截图，需留错误帧兜底；

4. scale 0.5 缩略图注意 devicePixelRatio 换算，保证时间线观感。

### P1-12（全局）Prompt cache 布局约束

W6/W7/W8/W10 的所有新增注入文本（页面地图、反思段、重规划说明、delta 反馈、state 后缀）必须放在缓存断点之后的**动态后缀区**，系统 prompt 与规划 prompt 保持字节稳定，防止打掉现有约 1/10 的多步成本优势。

本地 0.5B 链路的 prompt 模板**不要同步加入**反思段 /state 等新内容（0.5B 对这类结构的理解能力存疑，可能干扰直出质量），先仅在云端链路启用，用 W11 做 A/B 对照后再决定是否下放。

### P1-13（W6）页面地图建议延后，且修正 key 与内容



1. SPA 中 URL 做 key 不可靠（同 URL 不同弹窗、query 变化），应使用规范化 URL + 页面签名（heading 文本集合）；

2. yRange 在折叠面板展开、窗口缩放后会误导模型 ——**错误记忆比无记忆更糟**。只注入 "已确认事实"（如 "页面底部存在分页栏"），不注入易变的位置比例，或显式标注 "位置可能已变，以当前快照为准"；

3. 该项置信度最低（-15% 步数目标在 10 个 core 用例上可能根本测不出来），建议移出 v3.x 主线，延后 v3.4，2 人日让给 W4/W11。

## 三、P2 评估体系与排期修订

### P2-1（W11）回归集可信度三原则



1. **失败三分类进分母口径**：

* agent 失败（定位 / 规划 / 模型误判）—— 计入成功率；

* 环境失败（登录态过期、风控验证码、网络中断、公开站点改版）——**不计入** agent 成功率，单独列示；登录态失效自动暂停并标记 infra；

* 产品 bug（EasyBow 自身异常）—— 单独列示并建 issue；

  不做分类，优化方向会被环境噪声带偏。

1. **商业站点用例安全**：full 套件以只读任务为主；写操作用沙箱店铺 / 影子数据，禁止真实下单 / 支付链路；登录态人工预热保留。

2. **core 套件以本地 fixture 为主**（确定性、可无人值守），公开站点仅保留 2\~3 个冒烟用例（公开站本身不稳定，会污染基线）。

3. fixture 在方案已列 5 类（shadow 表单、遮罩按钮、同名元素、iframe 嵌套、React 受控组件）基础上，**必须再补 4 类**：

* 虚拟列表（验 P0-1）；

* 持续动画 / 倒计时页（验 P0-2 熔断）；

* WebSocket/SSE 常驻页（验网络静默过滤不误判）；

* canvas 页（验视觉通道兜底）；

* 另建议加：提交返回 500、提交开新标签（验 P0-3）。

### P2-2（W12）周报脱敏

traces 含客户订单号、账号、cookie 相关信息，`analyze-traces` 输出周报前必须经过脱敏（手机号、订单号、账号、URL token 参数），商业 ERP 交付场景下这是合规要求而非可选项。

### P2-3（W11 工期）

runner + 报告 + 9 类 fixture + 10 个 core 用例，3 人日偏紧，调整为 4\~5 人日。
