# EasyBow 优化方案（2026-10-08）

围绕三个诉求：①任务输入快速填充预设模板 ②AI 操作按"链式节点 + 预期复核 + 自愈重试"执行 ③更快更准的业界方案引入。
每节按「现状 → 方案 → 涉及改动 → 收益/成本」组织，最后给实施路线。

> 调研说明：本环境实时联网检索不可用（WebSearch 无返回），业界方案部分基于已公开的成熟开源实践
> （browser-use / Stagehand / Skyvern / WebVoyager / AgentQL / Playwright / prompt caching 等）整理，
> 仅 browser-use README 为在线核实来源。落地前建议对标注 ⭐ 的条目再做一次版本核实。

## 〇、现状速览（与三个诉求相关的结构）

```
右侧面板 TaskPanel.tsx        任务输入框（仅自由文本）→ startTask(task)
                                     ↓
agent/runner.ts  loop()       每步：提取元素 → 验证码检测 →（混合模式本地直出 / 云端调用）
                              → 执行动作批 → 错误文本塞回 lastResults → 下一步
agent/prompts.ts              无状态重组上下文（任务+页签+元素+记忆+摘要历史）
testcase/assertions.ts        expect 断言求值器（文本/选择器/取值/软断言）—— 仅测试模式使用
TaskEditorModal.tsx           4 个硬编码任务模板 —— 仅"大编辑器"里有
fastllm.ts                    Qwen2.5-0.5B int8 WASM 单线程本地快速决策
```

关键结论：

1. 模板已有雏形但入口太深：只有点「⤢ 大编辑器」才能看到 4 个写死的模板，主输入框没有任何快速填充入口，也不能自定义。
2. **普通任务模式没有"这一步是否达到预期"的复核环节**——模型说完就过，出错只是把 error 文本带给下一步，靠模型自觉纠正；而测试模式已经有完整的 expect 断言体系（预期→断言→判定→报告），两套能力没有打通。
3. 每步无状态重组上下文意味着**输入 token 每步重复计费**，且没有利用任何提示词缓存；本地快模型单线程 WASM 推理，加速上限有限。

## 一、任务输入快速填充预设模板

### 现状
- 模板只存在于 `TaskEditorModal.tsx` 的 `TEMPLATES` 常量（4 条，写死，不可改）。
- 右上角主输入框（`TaskPanel.tsx` 的 `.task-input`）只有自由文本 + 字数提示 + 大编辑器按钮。
- 定时任务、历史任务（有「复用此任务」）各自为政，没有沉淀为模板的通道。

### 方案
1. **快捷填充入口**（主输入框区域）：
   - 输入框下加一行可横滑的「模板 chips」（取最常用 3~5 条，一键填充到输入框，不清空已有内容时改为追加）；
   - 输入框左上角加 📄 按钮 → 下拉模板菜单（分组 + 搜索）；
   - **`/` 快捷触发**：输入框敲 `/` 弹出模板选择浮层，↑↓ 选择、Enter 填充、Esc 关闭（slash command 交互，成本低、上手快）。
2. **模板库可管理**：
   - 新增 `src/main/templates.ts` + 持久化（建议 `%APPDATA%/easybow/templates.json`，与 settings 同模式）；
   - 数据结构：`{ id, name, group, text, vars, pinned, ts }`；支持新增/编辑/删除/置顶/分组（如：跨页签搬运 / 信息采集 / 表单填写 / 流程操作 / 测试回归）；
   - **「保存为模板」**：历史任务详情里加「⭐ 存为模板」；大编辑器当前文本也可一键存模板；
   - 内置 4 条模板迁入该存储（首次启动做种子数据），大编辑器与主输入框共用同一份。
3. **变量占位符**（模板的灵魂，填充即填空）：
   - 语法 `{{日期}}` `{{时间}}` `{{昨天}}` `{{当前网址}}` `{{页签1标题}}` 等自动变量，填充时立即解析替换；
   - 自定义变量 `{{商品名:要搜索的商品}}`（带说明）→ 填充时弹一个小填空表单（模板内凡有自定义变量的字段列成输入行），填完生成完整任务文本；
   - 与定时任务天然契合：定时任务描述存模板变量，到点自动解析 `{{日期}}` 再执行。
4. **模板 ⇄ 其他子系统复用**：测试面板的"需求转用例"、定时任务新建都可从同一模板库取任务文本。

### 涉及改动
- 新增 `src/main/templates.ts`（CRUD + IPC）、`src/preload` 桥接、`src/shared/types.ts` 增加 `TaskTemplate` 类型；
- `TaskPanel.tsx`（chips 行 + `/` 浮层 + 📄 菜单）、`TaskEditorModal.tsx`（改为读模板库 + 存模板按钮）、`HistoryDropdown/TaskPanel` 历史项加「存为模板」。

### 收益 / 成本
- 收益：高频任务从"每次写一段话"变成 1~2 次点击；配合变量后定时任务、日常搬运任务零输入。
- 成本：小（1~2 天），纯前端 + 一层存储，不碰 Agent 循环，风险低。**建议第一个做。**

## 二、链式节点 + 预期复核 + 自愈重试（核心优化）

### 现状
- 普通任务是**纯反应式**：模型每步看页面 → 出动作 → 执行 → 有错也只是文本回传。"这一步做成了没有"没有任何显式判定，
  靠模型下一步自己看出来，一旦模型没看出来就一路错到底（比如点了没反应、填错字段、进了错误页面）。
- 测试模式已经有半套答案：`assertions.ts` 的确定性断言（文本/选择器/取值/软断言/3s 轮询）、`expect` 动作、
  步骤节点卡 UI（TestPanel 可编辑节点）、fail-fast——但只服务测试用例，普通任务用不上。

### 方案：把"步骤"升级为"节点"，每个节点 = 动作批 + 预期 + 复核门

```
计划阶段（任务开始，1 次）：模型输出节点链
  节点 N1: 意图=搜索商品        动作=click/type…   预期="页面出现搜索结果列表"
  节点 N2: 意图=读取前3条价格    动作=read_content  预期="拿到 3 条价格数据"
  节点 N3: 意图=切页签填写      动作=switch/type   预期="表单字段与记忆值一致"
  （渲染为时间线节点卡，用户可改预期、删节点、调整顺序——复用测试面板节点交互）

执行状态机（每节点）：
  planned → acting → verifying ─pass→ 下一节点
                       │
                     fail → recovering（自愈重试 ≤N 次）→ verifying（循环）
                       │
                    连续失败/同样错误 → escalated（暂停+通知+截图，等人工指路后继续）
```

**1. 预期怎么来**
- 计划阶段让模型为每个节点写「预期」：结构化 `expected: {type: 'text'|'url'|'selector'|'value'|'state'|'judge', ...}`，
  也可以只是自然语言（走 judge 复核）；
- 测试模式的用例步骤本来就带预期，直接复用（测试节点 = 硬断言节点）。

**2. 复核器分层（由便宜到贵，逐层放行）**

| 层 | 判定者 | 输入 | 成本 | 适用 |
|---|---|---|---|---|
| L0 确定性信号 | 本地代码 | 动作 error、URL/标题变化、可见文本（复用 `EXPECT_TEXT_FN`/`EXPECT_SEL_FN`）、表单值、`SOFT_ERR_FN` 表单错误、截图前后差异（感知哈希判"页面有没有变"） | 0 token，毫秒 | 一切可确定性验证的预期 |
| L1 快速决策模型 | 本地小模型 | 预期 + 动作结果 + 页面摘要（标题/URL/关键文本/OCR 片段）→ {pass\|fail\|uncertain} | 本地，0 token | 语义类预期的快速判定（"搜索结果出现了"） |
| L2 云端大模型 judge | 复用现有 provider | 同上 + 更完整上下文 → {verdict, reason} | 一次小调用 | L1 uncertain、关键节点 |
| L3 视觉复核 | VLM（视觉模式同款通道） | before/after 截图 + 预期 | 最贵 | 用户指定"优先视觉模型判断"的失败恢复、图标/图片类页面 |

配置项 `verifyMode: 'off' \| 'fast' \| 'strict'`：fast = L0+L1（默认，几乎零成本）；strict = 每节点过 L2；off = 维持现状。

**3. 失败自愈循环（对应诉求"让 AI 用自己对系统的理解，优先视觉模型判断来做出操作"）**
- fail 进入 recovering：下一步的提示词注入「节点预期 + 判定失败原因 + 前后截图」，并**自动开启视觉兜底**
  （复用现有 `VISION_FALLBACK_ADDON` + `click_xy` 看图定位），即"优先视觉模型判断来操作"；
- 同时注入问题经验库（`matchKB` 已有）与该域名历史成功轨迹——"用自己对系统的理解"落在这两处；
- 重试预算：每节点默认 3 次；**同样错误模式连续 2 次 → 不再盲目重试**，升级 escalated（暂停 + 系统通知 + 失败截图 + 自动填好"问题描述"的介入框），用户插话指路后从当前节点继续；
- 全部节点过审后才允许 `done`；`done` 前做一次**任务级验收**（拿任务描述 + 各节点结果让 judge 复核"任务真的完成了吗"），降低"以为完成了其实没有"的比例（这正是历史 👍/👎 反馈里 bad 的主因）。

**4. 与现有代码的打通**
- 复用：`testcase/assertions.ts`（确定性求值）、executor 的 `expect` 动作与 3s 轮询、TestPanel 节点卡交互、软断言；
- 改造：`runner.ts` 的 `loop()` 从"步"改为"节点内循环"（步数预算折算为节点×步）；`prompts.ts` 增加 `PLAN_PROMPT` / `VERIFY_PROMPT` / 恢复注入段；
- 新增：`src/main/agent/verify.ts`（L0~L3 复核器 + 判定聚合）、`src/main/agent/plan.ts`（节点链解析与持久化）；
- UI：时间线节点卡（预期、复核结果 ✅/🔄重试中/⏸待人工）、节点编辑入口（复用测试面板交互）。

### 收益 / 成本
- 收益：这是**准确率的最大杠杆**——错误被挡在节点边界内自愈，不再向后污染；用户全程看到"预期→复核结果"，可干预节点粒度。
- 成本：中大（核心 3~5 天 + 联调），动 Agent 主循环，需要回归现有 59 项自测。
- 风险控制：`verifyMode: off` 保底开关；先在测试模式之外只开 L0+L1（不加云端成本），观察一段时间再上 L2/L3。

## 三、更快更准：业界可引入的方案

### 准确率（accuracy）

1. ⭐ **Set-of-Marks 截图标注**（WebVoyager 系，视觉定位最有效的单点改进）
   现在发给模型的截图和元素列表是"两份材料靠 @x,y 坐标脑内对齐"。改成**把元素编号直接画在截图上**（半透明角标/圆点+数字）再发给 VLM，
   定位准确率显著提升。实现：离屏 canvas 把截图 + extract 的元素坐标合成（坐标已是视口绝对值，可直接画），成本半天。
2. ⭐ **约束解码 / 结构化输出**：OpenAI `response_format: json_schema`、Anthropic tool-use 强制、本地模型用 GBNF/xgrammar 约束——
   消灭 `parseModelJson` 失败重试（现在连续 3 次解析失败直接报错终止）。对 JSON 遵从度差的国产模型收益尤其大。
3. **无障碍树（aria snapshot）**：browser-use 新版的 axtree 路线，用 role + accessible name 替代/补充纯 DOM 列表，
   对图标按钮、自定义控件、语义歧义元素的描述更好；Playwright 有现成 aria snapshot 语法可参考。建议与现有元素列表并存（A/B 开关）。
4. **自愈定位器 / 语义选择器**（Stagehand、AgentQL 思路）：给关键元素存 `role + accessible name` 或语义描述的稳定定位器，
   元素编号刷新/失效时先按稳定定位器找回，再走重新提取——直接压低"元素已失效"类错误（当前视觉兜底就是被这类错误逼出来的）。
5. **轨迹复用（Agent Workflow Memory）**：任务成功后把（页面状态签名 → 节点动作序列）自动沉淀；
   相似任务（同站点同流程，如每天的订单搬运）直接走"经验捷径"，模型只做偏离部分的决策。现有的问题经验库(KB) + 历史 + 👍/👎 反馈是雏形，缺"自动沉淀 + 自动命中"。
6. **定位与决策分工**：GUI grounding 专用模型（UI-TARS、UGround、AriaUI、Qwen2.5-VL 系）在"点哪个元素"上强于通用大模型。
   可作为可选"定位器插件"：大模型只输出目标语义（如"提交订单按钮"），grounding 模型负责落到编号/坐标。
7. **任务级验收 + 反思**（Reflexion/Self-Refine）：done 前验收（见方案二）；失败节点让模型输出"错在哪、下一步怎么改"再行动，
   比直接重试成功率高。

### 速度（speed）

1. ⭐⭐ **提示词缓存（性价比最高）**：当前每步无状态重组上下文 → 输入 token 每步重复付费、TTFT 每步全量。
   把消息改成**稳定前缀 + 变化后缀**（SYSTEM_PROMPT + 任务 + 页签/记忆 + 历史摘要在前，元素列表/上一步结果在后），
   启用 Anthropic `cache_control` / OpenAI 自动缓存 / DeepSeek 上下文缓存（命中部分大幅打折且首字延迟显著降低）。
   `agent/llm.ts` 加缓存标记即可，提示词顺序需微调。对"每步重组"这个架构是量级级的省钱提速。
2. **并行化**：元素提取 ∥ 截图（现在串行）；OCR ∥ DOM 提取；动作批执行尾部与下一步提取预热（乐观预提取，页面未变时直接用）。
3. **本地快模型提速**：
   - 现状 `numThreads = 1`（主进程无 Web Worker）→ 移到 worker 线程/UtilityProcess 开多线程 WASM；
   - 或换 node-llama-cpp（GGUF Q4，支持 Vulkan/GPU）跑 Qwen2.5-3B 级，速度上一个数量级；或支持接 Ollama 本地服务（有 GPU 的机器）。
   - 更激进：快模型从"生成 JSON"改为**分类器**（下一步意图分类 + 参数槽填充），比自回归生成快得多。
4. **录制-回放**：第一次由模型走通的任务生成"动作脚本"，之后同流程任务直接回放（零模型调用），定时任务场景收益巨大；
   回放中任一节点复核失败 → 自动降级回模型驱动（与方案二的节点链天然衔接）。
5. **视觉模式省图**：默认关已有；再加"只在复核失败/视觉兜底时附图"、截图按视口缩放 + q60~70、`read_content` 同页缓存。
6. **量化回归基准**：建 10~20 个代表性任务的基准集（配合测试面板跑），度量「成功率 / 平均步数 / 平均耗时 / token」——
   现在只有 👍/👎 粗粒度正确率，没有它无法科学评估任何优化。**建议与方案二同期建。**

## 四、实施路线（建议）

| 优先级 | 内容 | 工作量 | 说明 |
|---|---|---|---|
| **P0** | 方案一：模板快速填充（chips + `/` + 模板库 + 变量） | 1~2 天 | 独立、零风险、立刻有感 |
| **P0** | 方案三之提示词缓存 + 元素提取/截图并行 | 1 天 | 纯性能，改动集中在 llm.ts / runner.ts |
| **P1** | 方案二：节点链 + L0/L1 复核 + 自愈重试（verifyMode 三档） | 3~5 天 | 准确率最大杠杆；先快档（零 token 成本），strict 后开 |
| **P1** | SoM 截图标注 + 约束解码 | 1~2 天 | 两个高性价比单点 |
| **P2** | 任务级验收 + 轨迹复用 + 基准集 | 2~3 天 | 依赖节点链落地 |
| **P2** | aria tree、语义选择器、grounding 模型插件、录制-回放、本地推理提速 | 按需 | 效果因站点/机器而异，逐项 A/B |

一个务实的组合拳：**P0 两项 + 方案二的"节点链 + L0/L1 复核"** 就能拿到大部分收益——
任务写得快了、每步做得对了、错了当场自愈，且不增加云端 token 成本；之后再按需叠加视觉复核与专用模型。
