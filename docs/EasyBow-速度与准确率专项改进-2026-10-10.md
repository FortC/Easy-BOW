# EasyBow 速度与准确率专项改进方案



* **日期**：2026-10-10

* **范围**：`E:/clb-pjs/Easy-BOW`（v3.0.1，Agent 主循环 / 元素提取 / 本地模型 / 动作执行 / 等待策略 / 节点复核）

* **背景**：作者实测「慢、而且不准确」，疑问是否与模型有关。

* **方法**：逐文件精读当前源码（不是看旧文档），对每条结论标注 `文件:行`，所有「多快 / 多慢」均为代码路径推演的**理论值**，落地前需要用第八节的基准方法实测确认。

* **结论一句话**：**慢，主要不是云端模型的锅，而是「本地 0.5B 模型串行前置 + 每步全页 OCR 增强 + 动作间拟人延迟 + 节点复核又一次本地生成」把单步耗时堆起来了；不准，是「0.5B 模型替大模型筛选 / 决策 / 复核三个环节都可能误判 + 纯文本元素列表跨步重编号 + 视觉模式没有编号标注（SoM）」共同导致的。** 云端模型的选择当然影响 JSON 稳定性和选元素能力，但它只占单步耗时的一小部分。

## 一、单步耗时解剖（理论模型，代码路径为证）

当前 hybrid 模式一个 step 的时序（数字为复杂后台页上的**估算区间**，待实测）：



```
t0  ┤ ① extract（CDP Runtime.evaluate，页内同步遍历整个 DOM）
    │   · querySelectorAll(SEL) + 逐元素 getComputedStyle + 逐大元素 elementFromPoint
    │   · shadow host 逐个 querySelectorAll('*')（extractor.ts:~154）
    │   耗时 0.15~1.5s（元素密集后台页偏高）
    │
t1  ┤ ② AX tree ∥ ③ 视觉截图 ∥ （④ 摩擦检测在提取后串行）   （runner.ts:1795-1799）
    │   · AX：getFullAXTree + 最多 80 个 DOM.getBoxModel，按 10 个一批【串行】 CDP（axtree.ts:78-92）
    │   耗时 0.1~0.4s（8 次 CDP 往返）
    │   · 视觉截图 JPEG q70 全尺寸（runner.ts:1788，仅视觉步/时间线需要时）  ~0.1~0.3s
    │   · 时间线常规步缩略图 q42 scale 0.5（runner.ts:2437）
    │
t2  ┤ ⑤ OCR 增强【串行】（runner.ts:1810-1814，无独立开关、无超时降级）
    │   命中 ≥1 个无文本小图/role=image 候选即：全页 PNG（ocr/index.ts:224）→ 隐藏窗口 IPC → det+rec 推理
    │   耗时 0（无目标时）~ 1~6s（图标密集页几乎每步）
    │
t3  ┤ ⑥ 节点规划仅首步额外 1 次云端调用（plan.ts，约 2~6s，与提取并行但阻塞首动作）
    │
t4  ┤ ⑦ 本地决策 decide()【串行】（runner.ts:1929-1967，fastllm.ts:49 硬超时 12s）
    │   严格门控，多数步骤不触发；触发且模型慢时 3~12s
    │
t5  ┤ ⑧ 本地预筛 prescreen()【串行】（runner.ts:1994-2022 → fastllm.ts:257-279）
    │   候选 >20 个就触发（默认 maxElements=80，真实页面几乎必然触发）
    │   提示词最多 60 个元素（fastllm.ts:260）+ 生成 64 token（fastllm.ts:265），
    │   单线程 WASM 0.5B：prefill+decode 约 2~6s
    │   genMs>8s 才永久禁用（runner.ts:2001-2004）——也就是说 ≤8s 的拖慢照单全收
    │
t6  ┤ ⑨ 云端调用（llm.ts:86/166，max_tokens=2048）
    │   一般 1.5~5s（gpt-4o-mini / DeepSeek / Claude 各有差异）
    │
t7  ┤ ⑩ 动作批执行（最多 5 个动作，逐个动作）
    │   每个 click：resolveIndex 1 次 evaluate（+失效时【重提取】）
    │              + sleep(160) + overlay.moveTo + 贝塞尔 10~18 次 CDP 事件（0.15~0.4s）
    │              + mouseClick 2 次 CDP + （toggle 再 resolve 一次）
    │   动作之间：humanDelay 280~650ms（executor.ts:456-459）
    │   type：聚焦后逐字符 60~140ms/字（cdp.ts:233-242，>50 字才整段）
    │   一个 3 动作批（含 1 次输入 8 个字）≈ 2~5s
    │
t8  ┤ ⑪ settle 自适应等待（executor.ts:631-716）
    │   waitNetworkQuiet(300,4000) ∥ waitDomStable(250,5000)，取先静默者
    │   轮询页/动画页吃满 4~5s；静态页也有 ~0.3s 静默门
    │
t9  ┤ ⑫ 节点复核（verify.ts，仅节点边界步）
    │   L0 确定性毫秒级；L1 本地 0.5B 生成（24 token、12s 超时）约 1~4s；L2 云端约 1.5~4s
    │   严格模式每个节点 +1 次云端调用；重规划另加 1~2 次
```

**典型单步合计（复杂后台页、hybrid 默认配置）**：约 **9\~16s / 步**。

其中真正「云端大模型推理」只占 1.5\~5s；其余 6\~11s 全是本地模型 / OCR / 拟人等待。

**这就是「hybrid 模式反而更慢」的根本原因 —— 设计来加速的本地模型，因为串行前置且预算太松，成了每步的固定税负。**

## 二、速度问题详表

### S1. 本地模型两次生成串行前置，预算过松（最大瓶颈）

**现状**



* 预筛触发条件仅为「hybrid ∧ prescreen ∧ 候选数 >20」（`runner.ts:1994`），没有「这次预筛值不值」的判断。

* 预筛提示词渲染最多 60 个元素（`fastllm.ts:259-262`），0.5B 单线程 WASM（`fastllm-worker.ts:51` numThreads=1）要 prefill 数千 token 再自回归生成 64 token。

* 云端调用在预筛完成之后才发起（`runner.ts:2082`）—— 完全串行。

* 单次 genMs 超过 **8s** 才永久关闭预筛（`runner.ts:2001-2004`）；decide 硬超时 12s（`fastllm.ts:49` GEN\_TIMEOUT\_MS=12000，超时还会 resetWorker）。

**改法：并行竞速（speculative race）**



```
提取完成
   ├── 立即发起云端调用（不等待本地）──────────────┐
   ├── decide（门控不变，预算收紧到 ~1.5s）         │
   │     └─ 命中且校验通过 → abort 云端 → 执行本地方案 │
   └── 若 decide 未尝试：prescreen（预算 ~1.2s）    │
         └─ 及时返回 → abort 云端 → 用 keepIdx 重发？│
                                                   ▼
                          本地预算超时/无效 → 取云端结果
```

注意两个细节：



1. **预筛的语义是「裁剪元素后再给云端」**，与「先开云端」冲突 —— 所以预筛竞速的正确形态是：**先按全量元素发起云端调用**；本地预筛若在云端首 token 返回前胜出且高置信，再取消云端、用裁剪列表重发（或干脆直接让本地 decide 基于 keepIdx 再出一次动作）。实现复杂时，第一版可只给 **decide 做竞速**（它本身就是完整替代云端），prescreen 暂时改为「预算 1.2s 超时即放弃，且本会话连续 2 次超时默认关闭预筛」（类似现有 settle 熔断，`executor.ts:577` 的思路）。

2. abort 云端请求用现成的 AbortSignal 机制（SDK 支持 `signal`）；注意部分中转对 abort 的请求仍计输入 token，加个设置项 `localRace` 默认开，用户可关。

**更彻底的方向（建议同期做，详见第五节）：用 embedding 模型替代生成式预筛**，预筛成本从秒级降到 10\~50ms，串行也无所谓，连竞速都不需要。

### S2. OCR 增强每步同步跑，无预算、无开关

**现状**：`runner.ts:1810-1814` 每步无条件 `await ocrEnhancer(extract, null)`；`ocr/index.ts:209-238` 只要视口内有 ≥1 个无文本小图 / 图片角色元素（面积 120\~60000px²、最多 10 个区域），就**重新截一张全页 PNG**（时间线截图刚截过一次，不复用）→ IPC 传给隐藏窗口 → det+rec 全图检测 + 区域识别。后台管理页顶部一排图标就稳定触发。

**改法（按代价从低到高，任选）**：



1. **按需触发**：只在「云端 / 本地方案里出现了无法定位的图片元素」或「视觉兜底恢复」时才跑 OCR 增强；普通步跳过。

2. **与云端调用并行**：把 OCR 增强放进 t1 的 `Promise.all`（和 AX / 视觉截图一起；摩擦检测本身很轻，保持原位即可），它产出的是元素文本补充，若在构建提示词（`runner.ts:2023-2044`）前完成就用，没完成就不用 —— 绝不阻塞决策。

3. **复用同一张截图**：让 t1 的截图直接输出 PNG buffer 给 OCR（CDP 截一次、按用途转码），省一次全页捕获。

4. 加设置开关 `ocrEnhance`（目前连开关都没有，只能整体卸载 OCR 模型）。

### S3. 拟人化默认开启的固定延迟，缺少「极速档」

**现状**（`humanLike` 默认 true，`speed` 只有 normal/slow）：



| 延迟点            | 位置                    | normal 档开销                                    |
| -------------- | --------------------- | --------------------------------------------- |
| 动作间 humanDelay | `executor.ts:456-459` | 每个动作 280\~650ms                               |
| 点击前固定 sleep    | `executor.ts:777,878` | 每次点击 160ms                                    |
| 贝塞尔鼠标移动        | `cdp.ts:248-271`      | 10\~18 次 CDP 事件 × (4\~16ms / 缓动) ≈ 150\~400ms |
| 逐字输入           | `cdp.ts:233-242`      | 60\~140ms / 字 + 每 8\~15 字 300\~700ms 停顿       |
| type 前后 sleep  | `executor.ts:906,908` | 60+140ms                                      |

一个含「点击搜索框→输入 8 字关键词→点击搜索」的批次，仅拟人延迟就约 **2.5\~4s**。对反爬场景这些延迟有价值，但对内部系统（聚水潭、自建后台）或开发调试完全是浪费。

**改法**：`speed` 增加 `'fast' | 'normal' | 'slow'` 三档：



* fast：动作间 0\~50ms、无贝塞尔（保留最后一个 mouseMoved 事件保证 hover 态正确）、输入整段 `insertText`、点击前 sleep 0；

* normal：现状；

* slow：现状的 slow（反爬敏感站点手工切换）。

* 进一步可按域名记忆档位（你们已有 host 级 settle 熔断记忆，`executor.ts:579-596`，同一套存储扩展即可）。

### S4. AX 树坐标批量查询是 8 次串行 CDP 往返

**现状**：`axtree.ts:78-92` 对最多 80 个 AX 节点逐个 `DOM.getBoxModel`，10 个一批，批间 await——8 次串行 WebSocket 请求 - 应答。

**改法（两档）**：



* 简单版：把同一批的 10 个 `send()` 先构造成 promise 数组再 `Promise.all`（现在是 for 循环内顺序 await），8 次往返变～1 次往返的耗时。

* 推荐版：**AX 文本根本不需要独立坐标**—— 提示词里的 AX 段（`axtree.ts:formatAxTree`）是给模型补充角色描述的，定位走 extractor 的编号 / 坐标。按 `role + accessible name` 与 extractor 候选做一次文本匹配，能匹配上的直接借用候选 rect；匹配不上的节点不显示坐标或不显示该节点。省掉全部 getBoxModel 调用。

### S5. 提取器内的强制同步布局开销

**现状**：`extractor.ts` 页内函数对每个面积 >400px² 的候选都调一次 `elementFromPoint`（遮挡检测，约 :230），对每个 shadow host 调 `querySelectorAll('*')`（约 :154）。`elementFromPoint` 会强制浏览器做一次 hit-test（可能触发 layout），数百个候选就是数百次强制布局，全部发生在被 await 的 `Runtime.evaluate` 内，直接计入 extractMs。

**改法**：



1. 遮挡检测不需要逐元素实时 hit-test：先一次性收集候选 rect，对**互相重叠的候选对**才做 elementFromPoint（大多数后台页候选不重叠，调用次数能降一个数量级）；

2. 或者用 IntersectionObserver 不行（异步且不直接给遮挡关系）—— 可改为批量检测：按中心点排序后只对「中心落在另一个更大元素 rect 内」的候选 hit-test；

3. shadow `querySelectorAll('*')` 改为沿 childElementCount 做有界遍历（已有 visited<60 上限，但 `*` 一次仍是全量子树收集），并把 shadow 穿透深度 / 节点数做成可配（现在写死 60 hosts、depth<4）。

### S6. settle 不分动作类型，read-only 动作也等网络静默

**现状**：每批动作之后统一 `Promise.all[waitNetworkQuiet, waitDomStable]`（`executor.ts:683-696`）。但 `scroll` / `read_content` / `wait` / `done` 这类动作并不触发 XHR/Document 请求，等 300ms 网络静默没有信息增益（scroll 可能触发懒加载，可单独保留 DOM 稳定等待）。

**改法**：settle 按批内最后一个有副作用的动作决定：



* 批内全是只读动作 → 只等 DOM 稳定 250ms（或直接进入下一步提取，提取结果相同则跳过模型调用，你们已有「页面无变化提示模型」的规则，把它前移为本地短路）；

* 批内含 click/type/select → 现状双信号；

* 批内含 submitish → 现状的新标签监听逻辑不变。

### S7. 节点规划 / 复核的额外模型调用偏多

**现状**：任务启动 1 次规划调用（`plan.ts`，3 次重试）；严格复核每个节点边界步 +1 次云端 L2；失败反思 +1；重规划 +1\~2。准确率换 token / 时延的权衡，但默认配置（locatorChain/reflection/replan/actionVerify 全开 + verifyMode=fast）在简单任务上也付规划税。

**改法**：



1. 规划调用改用**小 / 快模型**（设置里已有独立 planner 配置块，`settings.ts:111-128`，但默认跟随主模型）—— 文档推荐简单任务用 gpt-4o-mini/GLM-4-Flash 之类快模型规划，主模型执行；

2. 规划与首动作不必全串行：首步若是无歧义的开门动作（如任务第一步就是在当前页找搜索框），允许提取完成后先发起第一步云端调用，规划回来后仅用于后续节点标记（实现复杂，P2）；

3. L1 复核改 embedding / 确定性（见第五节），节点边界的 1\~4s 可基本消失。

### S8. 其他小项



* **max\_tokens 固定 2048**（`llm.ts:86,166`）：含 `paste_rich` 长 Markdown 的批次 JSON 可能被截断 → 解析失败 → 整轮重试（一次完整调用的代价）。检测到 paste / 长文本动作时动态提到 4096，或让长文走记忆 / 剪贴板侧信道，模型只传引用。

* **resolveIndex 失效时同步重提取**（`executor.ts:490`）：SPA 页面连续动作中可能多次触发；建议重提取结果直接替换为下一步快照并跳过该步 settle 后的重复提取（动作尾部乐观预提取，旧文档「并行化」里提过，未落地）。

* **structured probe**（`structured.ts`）开新模型时发 1\~2 个 1-token 预检请求，有缓存无大碍；建议把探测结果落盘（按 baseURL|model），重启不重探。

## 三、准确率问题详表

### A1. 0.5B 模型在三个环节替大模型做主，误判直接污染结果

0.5B 出现在三个地方，任何一处误判都会变成「AI 点错」：



| 环节               | 位置                          | 误判后果                                       |
| ---------------- | --------------------------- | ------------------------------------------ |
| **decide 本地直出**  | `runner.ts:1929-1967`       | 0.5B 从列表里选错编号 → 直接执行，云端完全没看过这一步            |
| **prescreen 预筛** | `runner.ts:1994-2022`       | 0.5B 把目标元素筛掉 → 云端只拿到 ≤12 个元素，**必然选错或被迫滚动** |
| **L1 节点复核**      | `verify.ts`（L1 本地 judge 分支） | 0.5B 误判「通过」→ 节点错误关闭并推进（代码策略是只把「通过」当定论）     |

其中 **prescreen 风险被现有兜底放大**：虽然保留了语义 top3，但 `semantic.ts` 是纯字面 + 同义词打分（没有向量语义），任务换个说法（如「把单子审核一下」vs 元素文案「审批」），top3 和 0.5B 可能同时漏目标，云端在 ≤12 个候选里无解。

**改法**：



1. 【10 分钟】修校验窗口缺陷：本地 prompt 只渲染前 30 个（`runner.ts:1950`），但 `validateLocalActions` 按全量候选数校验（`runner.ts:1957` → `fastllm.ts:302`）。0.5B 幻觉出 30\~89 的编号会通过校验并点击一个**它根本没见过的元素**。校验上界应改为「实际渲染数量」，并把 decide 门控 `localGateOk()`（调用处 `runner.ts:1942`）里算出的目标编号也限定在渲染窗口内（目标排在 30 名开外时不许本地直出，改为云端或先滚动 / 重排）。

2. 【0.5 天】预筛保留数从 12 提到～20，且**始终包含视口内评分 top-N**（如视口内前 8 个原样保留），保证模型至少看得到当前屏的主要控件。

3. 【1 天，见第五节】prescreen 与语义打分统一换 embedding 余弦检索；decide 保留但门控再加码：多候选同名（列表场景）、写操作、目标语义分低于阈值时一律云端。

4. 【0.5 天】L1 的「通过」分级处理：expectation 含明确关键词但页面文本没覆盖到关键词时，本地不得给 pass，只能 uncertain→L2（L1 在 `verify.ts:96-100`，页面文本只取 1200 字，`verify.ts:89`）。另外注意 `verify.ts:123,132,143` 仍保留「L2 不确定 / 调用失败 / 无法判定 → 按通过处理」（昨日评审 P1-12 只修了一半）：建议写操作节点和最终节点的异常一律按「不通过 / 转人工」，只读节点才允许 skip 放行，否则复核门在模型报错时形同虚设。

### A2. 元素编号跨步不稳定，模型无法形成「空间记忆」

**现状**：每步重新提取后都按「当前任务关键词」rerank（`extractor.ts:528`，在快照落盘前重排，编号即重排后编号）。页面轻微变化（展开一行菜单、出现一条 toast）就可能让同一元素的编号变化；而历史记录里写的是「点击 \[5]」，下一步 \[5] 可能已是另一个元素。

**改法：稳定编号（stable index）**



* 任务级维护一个 `Map<元素指纹, 稳定编号>`，指纹用现有的定位链思路：`role|tag ∧ 文本/aria/placeholder ∧ anchor 容器文本`（`executor.ts:519-527` 已有 anchor 消歧逻辑，抽出来复用）；

* 每步提取后：旧指纹命中的元素沿用旧编号（编号不要求连续，允许空洞），新元素从 `maxId+1` 开始；消失的元素编号不复用；

* 指纹一对多（同名列表项）时不分配稳定号，按 anchor 区分或标记为列表项让模型带上下文；

* 提示词里可以加一句「编号跨页保持，历史中的 \[n] 与当前 \[n] 指向同一元素（若仍存在）」。

* 这是 browser-use 新版的做法（index 跨快照粘滞），对减少重复动作、误点历史编号收益明显。

### A3. 视觉模式缺 Set-of-Marks（编号没有画在图上）

**现状**：视觉开启时，模型收到的是 q70 全尺寸 JPEG（`runner.ts:1788`，清晰度本身没问题）和一份独立的元素文本列表，**编号只存在于文本里**—— 模型要在脑内把 \[n] 贴到图上对应位置，小图标 / 密集后台页上极易错位；`click_xy` 又允许模型直接给坐标，错位没有任何护栏。旧优化文档（`OPTIMIZATION-PROPOSALS.md` 三 - 1）已点名但未落地。

**改法**：



1. 截图后用离屏 canvas（或主进程 `nativeImage` + 自绘）在每个候选**视口内位置**画编号角标（圆点 + 数字，与列表编号一致；SoM 标注图只给模型看，时间线 / 存档仍用原图）；

2. 进一步可做区域裁剪放大（模型上一步说要点右上角，就只截右上象限高清发送），在密集表格页比整页缩览更准；

3. 编号与 A2 的稳定编号统一，视觉 / 文本两条通道编号一致。

### A4. 文本模式不给坐标，模型缺少页面空间结构

**现状**：`runner.ts:2023` `formatForPrompt(extract, maxElements, useVision, keepIdx)`—— 纯文本模式下列表没有 `@x,y`，模型不知道元素在顶部 / 侧边 / 弹窗还是页脚，「左上角的菜单」「底部的下一页」这类空间指代无法落地。

**改法**：文本模式给**粗粒度网格坐标**（不增加多少 token）：把视口分成 8×6 网格，输出如 `[12] 链接 "首页" (网格 1,0)`，或直接给十位数精度的 `@120,40`；视觉模式继续给精确坐标。配合 A2 稳定编号效果更好。

### A5. 多动作批在页面跳转后继续用旧编号执行

**现状**：一批最多 5 个动作顺序执行（`executor.ts:746+`），若中间某个 click 引发了导航 / 大重渲染，后续动作的编号已失效 —— 虽然 `resolveIndex` 有重定位链兜底（`executor.ts:482-575`），但重提取会**整体替换快照**，列表场景（同名行）靠 anchor 仲裁仍可能错行。

**改法**：动作批执行中检测「硬页面变化」（URL 变化 / 同序号 path 解析失败且重提取差异度 > 阈值，如 40% 候选指纹变化），立即终止本批、把「页面已跳转，剩余动作已取消」回传，让模型基于新页面重新出批。写操作动作之后默认强制断批（submitish 之后本来就有新标签处理，扩展到普通导航即可）。

### A6. rerank 误提升与 boosted 提取触发条件偏字面

**现状**：`rerankByTask` 把所有语义分 ≥0.5 的元素整体提前（`extractor.ts:536-539`），任务里出现的常见词（「订单」「确定」）可能把一堆无关元素提到前面，挤掉视口内真正显眼的主操作；boosted 提取只在「一个关键词都没命中」时触发（`runner.ts:1806-1809` + `executor.ts:401-406`），只要有一个泛命中就不扩容。

**改法**：



1. rerank 只提前 top-K（如 8 个，参数 `topBoost=8` 其实已传入但函数里把**全部** ≥0.5 都提到前面，改为只取 `topBoost` 个）；

2. boosted 触发改为「视口内候选的最高语义分 < 阈值」而非全量零命中（现触发条件在 `runner.ts:1820-1826`，判据函数 `executor.ts:401-406`）；

3. 长期交给 embedding（第五节），阈值含义从「字面命中」变成「余弦相似度」，可标定。

### A7. 视觉兜底 click\_xy 缺少「图→点」准确率的度量与护栏

**现状**：`executor.ts:846-887` 用 `VIEWPORT_FN`（visualViewport/innerWidth）把 0\~1000 归一化坐标换算到 CSS 像素，DPR / 滚动换算链路是正确的；命中元素也会记录进 hits（`executor.ts:860-871`）。真正的短板是：模型在**没有编号标注的整页图**上估坐标，密集小图标天然偏差大（A3），而 hit-test 结果只用于时间线展示，没有统计回流。

**改法**：随 A3 一起解决（SoM 后优先让模型回编号，click\_xy 仅留给 canvas / 无编号目标）；并把时间线命中标记里「模型给的点 vs 实际命中元素 tag/text」持久化到 telemetry，统计「坐标准确率」作为基准指标（第八节），让视觉通道的好坏可度量。

### A8. 其他准确率细项



* **iframe 穿透深度 depth<2**（`extractor.ts` 旧评审 P2 未修）：支付 / 广告第 3 层 iframe 元素永不入列，遇到只能上视觉坐标；建议提到 3 并加总节点预算防爆炸。

* **toggle 回读依赖重解析**（`executor.ts:792-805`）：自定义 switch 的 checked 语义可能读不到，回读失败时静默无提示；建议回读失败在结果里明示「状态未知」而非不说话。

* **done 偏乐观**：节点链开启后由节点全完成门控（已大幅改善），但无节点规划成功时（plan 失败 / 被关）仍靠模型自觉；建议 done 前若本任务存在未命中过的任务关键词（复用 `extractKeywords`），要求模型解释或自动转一次 L2 轻量验收（不必整图，标题 + URL + 视口文本即可，成本很低）。

* **温度 0.2**（`runner.ts:101`）合适，别动；但建议对 decide/prescreen/verify 的本地生成显式 greedy（worker 里已是 `do_sample:false`，正确）。

## 四、「和模型有关吗」—— 分环节回答

有关，但要分清楚**哪个模型**影响**什么**：



| 环节           | 现在用什么                      | 对「慢」的影响           | 对「不准」的影响                      |
| ------------ | -------------------------- | ----------------- | ----------------------------- |
| 云端主决策        | 用户配置（默认 gpt-4o-mini）       | 中：1.5\~5s / 步，占比小 | **大**：JSON 遵从度、长列表选编号、跨页推理全靠它 |
| 本地 decide    | Qwen2.5-0.5B int8，WASM 单线程 | 大：触发时 3\~12s      | 中：门控严格但仍会选错编号                 |
| 本地 prescreen | 同上                         | **很大：几乎每步 2\~6s** | **大：筛错了云端也救不回来**              |
| 本地 L1 复核     | 同上（24 token）               | 中：节点边界步 1\~4s     | 中：假通过推进错误节点                   |
| OCR          | PP-OCRv4 WASM              | 图标页每步 1\~6s       | 小～中：标签补错会误导                   |

**结论**：



1. 你感觉的「慢」，**大概率不是云端模型慢，而是本地模型和 OCR 的串行税负**—— 建议立刻做一组对照实验：设置里分别用「纯云端」和「混合」跑同一个 10 步任务，对比 `StepTimings` 汇总。如果纯云端反而更快，就证明是这个问题（第八节给了方法）。

2. 你感觉的「不准」，**云端模型和 0.5B 各背一半锅**：纯云端模式下还不准，才是云端模型 / 提示词 / 编号问题；混合模式特有的不准（目标被预筛筛掉、0.5B 直出点错），按 A1 修。

### 云端模型选择建议（按这个任务的能力需求排序）

这个任务对模型的要求是：**长指令遵循 + 从 80 行编号列表里精确选号 + 严格 JSON/tool-use**。按公开口碑和该类任务（WebArena/OSWORLD 风格）的普遍表现：



* **第一梯队**：Claude Sonnet 级（3.5/3.7/4 系，列表选号与工具调用最稳）、GPT-4o / GPT-4.1 级；

* **性价比梯队**：**gpt-4o-mini（当前默认，够用）**、DeepSeek-V3.1（中文页面、长上下文性价比高，注意 JSON 严格度偶发波动 —— 你们的结构化降级链已经兜住）、GLM-4.5/GLM-4-Flash（快、便宜，适合做 planner）、Qwen3 系列（中文后台页表现不错）；

* **不建议用于主决策**：7B 以下本地开源 VLM/LLM、各类「极速版」蒸馏小模型 —— 编号选择错误率明显高，省的 token 不够重试的成本。

* 建议做法：**主模型用第一梯队或性价比梯队，planner 固定配一个快模型**（设置里 planner 独立配置已经做好了，`settings.ts:111-128`，把它用起来）。

### 本地模型路线建议

0.5B 单线程 WASM 做**生成式决策**，能力和速度都到顶了，继续调 prompt 收益很小。三条路线：



1. **【推荐】把 0.5B 的生成式任务换成 embedding 模型**（第五节）：bge-small-zh /gte-small 级（30\~100MB，CPU 上单次数毫秒到几十毫秒），预筛、语义打分、L1 关键词复核三个场景全部覆盖，又快又稳；0.5B 仅保留 decide 直出或干脆下线。

2. **升级到 1.5B\~3B + WebGPU**：关键工程技巧 ——**复用你们 OCR 的「隐藏 BrowserWindow」模式**（`ocr/index.ts:43-63`）：渲染进程里有 `navigator.gpu`，onnxruntime-web 的 webgpu EP 可以在隐藏窗口里跑 GPU 推理；utilityProcess 里没有 WebGPU 才被迫 WASM 单线程（`fastllm-worker.ts:4-13` 的约束）。3B q4 在核显上也有 20\~40 tok/s，decide/verify 都能进 1s。模型可选 Qwen2.5-1.5B/3B-Instruct，或 GUI 专用的 UI-TARS 系列（7B，专门为「截图→动作」训练，适合做视觉档定位器，较重）。

3. **接 Ollama /llama.cpp server**：让有 GPU 的用户自带本地服务，应用只发 HTTP（你们已有 baseURL 中转体系，加一个 provider 即可），维护成本最低。

## 五、推荐架构：embedding 预筛 + 并行竞速（目标形态）



```
                         任务启动
                            │
              任务文本 → embedding（每任务一次，缓存）
                            │
每步：提取 extract ──────────┤
   ├─ 候选文本批量 embedding（页面级缓存：DOM 签名不变不重算，复用 domstable 的 Mutation 指纹思路）
   ├─ 余弦相似度 top-K 预筛（毫秒级，替代 0.5B prescreen）   ── 同步给 rerank（替代字面打分）
   ├─ AX/截图/摩擦/OCR增强 全部并行（OCR 设预算、不阻塞）
   │
   ├─ 决策竞速：
   │    ├─ 云端调用（全量/embedding-topK 元素，立即发起）
   │    └─ 本地 decide（严格门控，1.2s 预算）→ 赢则 abort 云端
   │
   ├─ 动作批执行（极速/拟人三档；硬页面变化立即断批）
   ├─ settle（按动作类型分流；动作尾部乐观预提取下一步元素）
   └─ 节点复核：L0 确定性 → embedding/关键词 L1（毫秒）→ 仅高价值节点 L2 云端
```

embedding 预筛的最小实现（transformers.js，与现有技术栈完全一致）：



```
// 伪代码：用 @huggingface/transformers 的 feature-extraction pipeline
// 模型建议 Xenova/bge-small-zh-v1.5 或 gte-small（int8 几十 MB，WASM 也很快）
const extractor = await env.featureExtraction('Xenova/bge-small-zh-v1.5')
const taskEmb = await extractor(taskText, { pooling: 'mean', normalize: true)

// 每页一次：候选文本批量编码（短文本，几十~几百条，CPU 上几十~几百 ms）
const candText = candidates.map(c => `${c.role} ${c.text} ${c.extra}`.trim())
const candEmbs = await extractor(candText, { pooling: 'mean', normalize: true })

// 余弦（normalize 后即点积）top-K，比 scoreCandidate 的字面同义词鲁棒得多
const scored = candEmbs.map((e, i) => ({ i, sim: dot(taskEmb, e) }))
const keep = new Set([...topK(scored, 16).map(x => x.i), ...viewportTopN(8)])
```

落地顺序建议：先让 embedding **替换&#x20;**`semantic.ts`**&#x20;的打分**（纯函数替换，自测好写，`selftest.ts:942` 已有 rerank 用例可扩展），验证准确率提升后，再替换 prescreen，最后接管 L1。每步都可独立回滚（开关照抄 v3 的独立开关模式）。

## 六、动作尾部乐观预提取（pipeline 优化）

现在每步是严格的「settle 完 → 下一步才开始提取」。实际上 settle 的后段（网络静默窗口）页面 DOM 往往已经稳定：



```
现在：  动作批 ├─ settle（最长 5s，后段在空等）┤─ 提取 ┤
改后：  动作批 ├─ settle ┤─ 提取（在 settle 探测到首次静默时就发起）┤
                         提前 0.3~2s
```

实现要点：



1. `waitDomStable` 探测到首次静默（250ms 无结构变动）时即返回（现在已是这个语义），返回后立即提取，不再等网络静默的完整上限 —— 网络静默只对 submitish / 有 XHR 的动作重要，那类动作保留双等待；

2. 提取结果加 DOM 签名（`domstable.ts` 的 MutationObserver 已经在数变动，顺手输出一个简单 hash：关键元素 tag+text 的采样哈希）；下一步真正开始时若签名未变，直接复用预提取快照（包括 embedding），变了就重提；

3. 这与 A5 的断批检测共用同一个签名机制，一套基建两个用途。

## 七、视觉通道专项（视觉模式用户）



1. **SoM 编号标注**（A3，P0）：编号圆点画在候选 rect 中心或左上角；被遮挡 / 视口外的不画或半透明；标注图层与 overlay.ts 的点击光晕用同一套坐标换算（CDP CSS 像素，已有现成代码）。

2. **截图策略分级**：文本模式默认不附图（现状）；视觉图维持 q70 全尺寸（现状已如此，不要再为省 token 降采样，小文字会直接丢定位信息），密集场景改走上一条的区域裁剪放大；恢复 / 复核场景附「before/after 两张」时，after 用当前视口、before 从时间线存档取（已在做）。

3. **可选 grounding 模型插件位**：预留一个「定位器」接口 —— 云端主模型只输出目标语义（「审批通过按钮」），定位器（UI-TARS / Qwen-VL 系 / 或 embedding + 编号）负责落到编号。先不实现，接口先抽象，避免后续改主循环。

## 八、度量：没有基准就无法证明改好了

你们已经有 `StepTimings`（extractMs 记录于 `runner.ts:1802`、llmMs 于 `runner.ts:2126`、genMs 来自 `fastllm.ts`、settleMs 由 executor 回填）和 telemetry，缺的是**汇总视图和固定任务集**：



1. **固定基准集**：从 `resources/test/regression/cases.json` 和日常任务里选 10\~15 个代表任务（信息采集 / 表单 / 跨页签搬运 / 图标密集后台 / 轮询页面各 2\~3 个），每个任务定义「成功判据」（复用节点预期 /expect 断言）。

2. **跑分模式**：每个任务在 4 种配置下各跑 3 遍：

* 纯云端（hybrid 关）

* 混合现状

* 混合 + 竞速

* 混合 + embedding 预筛

  统计：成功率、平均步数、**单步 p50/p95 耗时及各阶段拆分**、本地命中率（decide 直出占比 / 预筛耗时分布）、云端 token、重试次数。

## 十一、已经做对、不要再重复造的部分

评审中确认以下机制已经是业界主流做法且实现正确，优化时不要破坏：



1. **编号元素列表 + 快照编号契约**（browser-use 同款，比纯坐标法稳）；

2. **Anthropic prompt caching 标记 + 缓存友好的提示词布局**（`llm.ts:164-178`、`prompts.ts:19-32`）；

3. **提取 ∥ AX ∥ 视觉截图并行**（`runner.ts:1795-1799`；摩擦检测紧随提取之后串行，开销很小）；

4. **DOM 稳定探针替代 networkidle**（`domstable.ts` 分类表 + `waitDomStable`），且有连续吃满熔断回退固定等待（`executor.ts:577-596`）—— 比绝大多数开源 demo 的 sleep/networkidle 先进；

5. **定位链自愈**（path → anchor 联合消歧 → 文本 → role → 坐标命中护栏，写操作禁裸坐标，`executor.ts:482-575`）；

6. **节点链 + L0/L1/L2 分级复核 + 反思 / 重规划**（`plan.ts`/`verify.ts` + runner 主循环内节点门控段），方向与最新 agent 研究一致；

7. **结构化输出探测与运行时降级**（`structured.ts`，json\_schema→json\_object→纯文本）；

8. **trusted 输入管线**（CDP Input.dispatch\* /insertText，React 受控组件原生 setter 兜底）；

9. **本地模型在 utilityProcess、OCR 在隐藏窗口**，主进程零阻塞，失败安全回退云端；

10. **settings 白名单校验 + safeStorage 加密 apiKey + 原子写盘**（昨天评审的 P1 项已修复）。
