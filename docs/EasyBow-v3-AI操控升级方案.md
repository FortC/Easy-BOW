## 一、结论先行（TL;DR）

### 1.1 对齐度总评

按参考方案的「三代技术路线」划分，EasyBow **已经是第三代混合路线**（结构化元素列表为主 + 视觉 / OCR 兜底 + 本地小模型加速），方向没有走错，不需要换路线、不需要引入 browser-use/Playwright MCP 原库。六支柱中 **3 项达标、1 项部分达标、2 项是明确短板**：



| 参考方案支柱        | EasyBow 现状                                          | 评级                |
| ------------- | --------------------------------------------------- | ----------------- |
| 支柱 1 有限动作原语   | 25+ 个有限动词，模型做选择题                                    | ✅ 达标              |
| 支柱 2 ref 失效重拍 | 每步重提取 + resolveIndex 失效重定位                          | ✅ 达标（定位键可加强 → W4） |
| 支柱 3 智能等待     | **固定 sleep 为主**（600/1200ms settle、280\~650ms 批内间隔）  | ❌ **最大短板 → W1**   |
| 支柱 4 定位策略链    | 单一 DOM path 索引 + tag+text 重定位仲裁                     | ⚠️ 部分 → W4        |
| 支柱 5 平面分离     | 弹窗 / 文件上传 / 页签 / 同源 iframe 均正确处理；**Shadow DOM 未穿透** | ⚠️ 部分 → W5        |
| 支柱 6 验证闭环     | 节点链 L0/L1/L2 复核 + 填后语义校验 + 测试断言，**超出参考方案水平**        | ✅ 领先              |

Agent 层（参考方案第四章）：规划 / 执行分离 ✅、模型分级（本地 + 云端）✅、记忆机制 ⚠️（无页面地图）、**反思机制 ❌（无失败策略记忆）、动态重规划 ❌（一次规划定终身）**。评估体系 ❌（有 telemetry 埋点，无任务级回归集与成功率度量）。

### 1.2 「不丝滑」的三大根因（按贡献度排序）



1. **固定等待海**：每批动作后无条件 `sleep(600/1200ms)`（`executor.ts:435-446`）+ 批内每个动作间 280\~650ms + 点击前 160\~220ms + read\_content 阅读停顿 400\~1500ms。30 步任务累计 **20\~60 秒纯等待**，且页面快时白等、页面慢时没等够。

2. **每步无条件截图**：`runner.ts:2007` 每步都 `screenshotJpeg()` 给时间线（视觉模式关闭时也拍），每张 100\~300ms。

3. **串行小开销叠加**：AX 树取盒子分 8 批串行 CDP 往返（`axtree.ts`）、AX 与提取未并行、批间 settle 与 humanDelay 叠加。单步非 LLM 开销合计 1.5\~3s。

### 1.3 「不够智能」的三大根因



1. **一次规划定终身**：`buildPlan` 只在任务开始调用一次（`runner.ts:1406` planAttempted 门卫），跑偏后只会「同节点重试 → 升级人工」，**从不带着失败上下文重新规划**。

2. **没有反思记忆**：模型看不到「我刚才已经试过什么、为什么失败」的结构化清单，同一个动作可以换着姿势反复撞墙（现在靠 loop 类诊断 3 次后直接暂停人工）。

3. **单云端模型兜底一切**：规划、执行、复核全用同一个模型配置；失败升级链的终点是「人工」，而不是「更强的模型」。

### 1.4 Top 6 改造项（ROI 排序）



| # | 改造项                                       | 解决什么                 | 工作量    |
| - | ----------------------------------------- | -------------------- | ------ |
| 1 | W1 智能等待体系（DOM 稳定信号 + wait\_for 原语 + 网络静默） | 丝滑 + 提交类操作成功率        | 3 人日   |
| 2 | W7+W8 反思机制 + 动态重规划                        | 「笨」的核心：不重蹈覆辙、会绕路     | 4 人日   |
| 3 | W2 步内开销削减（截图惰性化 + 并行化 + 去叠加等待）            | 丝滑                   | 2 人日   |
| 4 | W4 语义定位链（role+name 定位键 + AX 融合升级）         | 页面异变下点得准             | 4 人日   |
| 5 | W11 任务回归集                                 | 让后续所有优化「有数字可依」，不再靠体感 | 3 人日   |
| 6 | W10 动作后轻量核验                               | 禁止模型「脑补」，点没点中立即可见    | 1.5 人日 |

## 四、P0 丝滑提速

### W1 智能等待体系（对应参考方案支柱 3—— 本次改造的第一优先级）

**现状与差距**：`executor.ts:435-446` waitSettle 在 isLoading 结束后**无条件固定 sleep 600ms（慢速 1200ms）**；`wait` 动作是裸 sleep；提交类点击后的检查也是固定 1.2s。参考方案明确：「固定 sleep 是又慢又不稳的万恶之源」。

**设计**（三层信号，从可靠到兜底）：



1. **DOM 稳定探测替代固定 settle**：

* 注入常驻探针脚本（extract 时顺带安装）：MutationObserver 记录「最近一次 DOM mutation 时间戳」，双 rAF 校验。

* `waitSettle` 改为：`isLoading=false && 距最近 mutation ≥ 250ms` 即返回；总上限 8s；保底 120ms。

* SPA 路由切换（无 isLoading 变化）同样被 mutation 静默期覆盖。

1. **新增&#x20;**`wait_for`**&#x20;动作原语**（模型可用的表达式等待）：



```
{"name":"wait_for","kind":"text_visible|selector_exists|url_contains|network","value":"提交成功","seconds":8}
```



* text/selector/url 复用测试模式 expect 的轮询实现（`executor.ts:964-1058`，3s 上限提到可配，默认 8s）；

* `network` 类：等「URL 含某片段的请求出现且响应完成」，复用 `cdp.findResponseBody`（`cdp.ts:446-490`），**把网络捕获从测试模式开放给普通任务**（Network.enable 常开，捕获环形缓冲仅保留最近 50 条，内存可控）。

* 提示词 `SYSTEM_PROMPT` 增加 2 行说明；`wait` 原语保留（向后兼容）。

1. **提交类点击自动等业务信号**：click 到 submitish 元素（已有判定 `/提交|确定|保存|下单|支付/…`）后，自动执行「网络静默 300ms + DOM 稳定」等待（上限 5s）再返回，替代现在的固定 1.2s 软断言等待 ——**等待期间页面自己会把结果渲染出来，下一步提取即可见**。

**边界与保守策略**：



* 慢速模式（风控敏感站点）**保留原固定节奏**，信号等待只做提前退出条件不放宽间隔；

* networkidle 不采用（参考方案同样警告长轮询页面永不 idle）。

**涉及文件**：`executor.ts`（waitSettle/wait\_for/ 提交等待）、`cdp.ts`（mutation 探针注入 + 网络捕获常开化）、`prompts.ts`（wait\_for 说明）、`runner.ts`（透传）。

**验收**：



* telemetry 新增 step 级计时字段（extractMs/settleMs/llmMs/actMs）；

* 「聚水潭读 3 条订单填入淘宝搜索」基准任务：平均每步耗时下降 ≥30%，成功率不降；

* 慢速模式行为逐字节不变。

**工作量**：3 人日。

### W2 步内开销削减

**现状与差距**：



* `runner.ts:2007`：视觉模式关闭时**每步仍无条件截图**给时间线；

* AX 树取盒子：80 节点 ÷ 每批 10 = 8 轮串行 CDP 往返（`axtree.ts:71-94`），且 AX 在元素提取**之后**串行执行（`runner.ts:1479-1485`）；

* 批间 waitSettle（600ms）与批内 humanDelay（280\~650ms）在批尾叠加。

**设计**：



1. **时间线截图分级**：常规步拍低清缩略图（scale 0.5、q30，约 40\~80ms）；**动作出错的步与 done 步拍高清**（executed 返回后再决定清晰度，顺序天然成立）；视觉模式步本来就有高清截图，直接复用不再重拍。设置项 `timelineShot: 'all'|'smart'|'off'`，默认 smart。

2. **AX 并行化**：fetchAxTree 与 extract、screenshot 一起进 `Promise.all`；盒子查询批大小 10→25、单项超时 5s→3s。

3. **去叠加等待**：批尾 waitSettle 已含等待语义，批内最后一个动作后的 humanDelay 取消（只保留动作之间的）。

4. **read\_content 阅读停顿**只在 humanLike 开启时保留（现状已是），但上限 1500ms→900ms。

**涉及文件**：`runner.ts`、`executor.ts`、`axtree.ts`、`settings.ts`/`types.ts`（timelineShot 项）。

**验收**：非 LLM 单步开销（extract→AX→执行→settle→截图）P50 < 800ms（telemetry 计时）；时间线体验不降（缩略图点击仍可放大，只是默认分辨率降低）。

**工作量**：2 人日。

### W3 结构化输出强化

**现状与差距**：`parseModelJson` 宽松解析（剥围栏、截大括号），模型偶发输出散文导致整步浪费（连续 3 次才报错，`runner.ts:1790-1808`）。参考方案：「强制结构化输出（JSON schema）」。

**设计**：



* OpenAI 兼容协议：探测式启用 `response_format: {type:'json_schema'}`（构造与现有动作契约一致的 schema，`additionalProperties:false`），首次 400 即会话内降级 `{type:'json_object'}` 再降级裸调用 ——**三级探测、零配置**；

* Anthropic 协议无原生 schema，保持现状（已有 cache\_control 加持）；

* 解析失败率、降级层级写入 telemetry；

* 连续解析失败阈值 3→2，第 2 次起 user 消息附带一个「正确输出示例」few-shot 片段。

**涉及文件**：`llm.ts`（response\_format 探测）、`runner.ts`（few-shot 注入）。

**验收**：解析失败步占比 < 0.5%（telemetry 度量）。

**工作量**：1\~1.5 人日。

## 五、P1 感知与定位升级

### W4 语义定位链（对应参考方案支柱 4）

**现状与差距**：元素定位唯一落点是 **DOM children 索引路径**（`Candidate.path`），SPA 重渲染插入任意节点即断链；失效后的重定位仲裁依赖 `tag+text 全等 + 中心点最近`（`executor.ts:414-428`），遇到文案为空 / 重名元素仍会错位。AX 树目前只是「文本线索不足候选」的补丁（≤40 个叠加）。参考方案定位链首选 **role + accessible name**——「用户在页面上能看到的文字，与无障碍树 name 天然一致，最抗改版」。

**设计**：



1. **快照候选携带定位键**：extract 时为每个候选持久化 `loc: {role, name, aria, placeholder, text, tag}`（AX 树已算出 role/name，DOM 提取已有 placeholder/text/aria—— 只差合并落字段）。

2. **resolveIndex 升级为四级定位链**：



```
① framePaths+path（现行，最快）
② role+accessible name 唯一匹配（AX 融合后天然可得）
③ aria/placeholder/text + tag 匹配（唯一才用；多个时按中心点最近）
④ 快照 rect 坐标兜底（页面未滚动时直接点，配合 click 后核验 W10）
```



1. **AX 树从补丁升格为并联主源**：上限 80→150；role/name/state（disabled/checked/expanded）写入候选（不再只在文本线索不足时叠加）；state 进元素列表行内（`[7] button "提交" (disabled)`），模型可据此避免点死按钮 ——**这是现在完全没有的信息**。

2. 编号契约不变（提示词格式零破坏），融合发生在快照落盘前。

**涉及文件**：`extractor.ts`（Candidate.loc 字段）、`axtree.ts`（上限与 state）、`executor.ts`（resolveIndex 定位链）、`formatCandidates`（state 渲染）。

**验收**：



* 自建「破坏测试页」：点击后脚本主动插入节点 / 改 DOM 结构 / 复制同名按钮，四级链重定位成功率 ≥90%（现基线先行测量）；

* 聚水潭 / 淘宝真实回归任务成功率不降。

**工作量**：4 人日。

### W5 Shadow DOM 穿透 + 跨域 iframe 增强

**现状与差距**：`EXTRACT_FN` 用 `doc.querySelectorAll`（`extractor.ts:236`），**shadow DOM 内元素完全不可见**（部分低代码平台 / 组件库站点整个表单都在 shadow 里）；跨域 iframe 现为「尽力提取」。

**设计**：



1. 遍历改为 **composed tree 递归**：`querySelectorAll` 收集后，对每个元素的 `shadowRoot` 递归 collect（含 open shadow；closed shadow 无法穿透，同所有竞品）；

2. path 定位对 shadow 元素失效 —— 正好由 W4 定位链②③兜底（shadow 元素用 role+name/text 定位）；rect 换算同 iframe 累加祖先 shadow host 偏移；

3. 跨域 iframe（OOPIF）：一期先做「探测 + 告知」—— 检测到 OOPIF 时在元素列表尾部注明「检测到 N 个跨域 iframe（URL…），其中元素暂不可见，如需操作请尝试视觉模式」；完整 OOPIF 穿透需要 CDP `Target.setAutoAttach` 独立会话，列为 v3.4+ 候选，本期不做。

**涉及文件**：`extractor.ts`（递归 + 偏移换算）、`resolveIndex`（配合 W4）。

**验收**：用 Lit/Vue 组件库（shadow DOM 表单）搭建的测试页，元素可提取、可点击、可输入。

**工作量**：2\~3 人日。

### W6 页面地图（任务内短期记忆）

**现状与差距**：同任务内模型对「这个站点布局」没有记忆，翻页采集 / 多区域表单场景反复滚动探索。参考方案 4.4「页面地图：哪个区域有什么功能，减少重复探索」。

**设计**（轻量版，不做向量库）：



* 任务内维护 `pageMap: Map<URL模式, {regions: [{desc, yRange}], lastScroll}>`：从已执行步骤的候选分布自动聚类出「导航区 / 表单区 / 列表区」粗粒度区域；

* 注入提示词一行：「本页上次已探索区域：表单在中部（滚动 40%\~60%），列表在底部」，帮模型跳过盲目滚动；

* 任务结束即弃（不落盘，与经验库职责分离）。

**涉及文件**：`runner.ts`（pageMap 维护）、`prompts.ts`（注入行）。

**验收**：翻页采集类任务的平均步数下降 ≥15%。

**工作量**：2 人日（优先级最低，可延后）。

## 六、P2 Agent 层智能化

### W7 反思机制（对应参考方案 4.2 Reflection）

**现状与差距**：失败后有七类归因和分类 hint（很好），但**模型看不到结构化的「已尝试方案」清单**—— 同一个目标换个 index 再撞、或换回原来的动作，全靠模型自觉；loop 类诊断（同动作名连续 3 次失败）直接暂停人工，缺中间档。参考方案三要点：记录失败动作、**同一失败动作禁止重复第二次**、失败上下文含已尝试列表。

**设计**：



1. **失败签名登记**：`tried: Map<目标签名, Array<{action, error, ts}>>`，目标签名 = 动作名 + 候选文本 /name（而非 index——index 每步都变）。

2. **注入反思段**：构造 user 消息时，若当前目标签名已有 ≥1 次失败，拼一段：



```
# 反思（该目标此前已尝试过，禁止重复同样方式）
- 尝试1: click "登录" → 失败:元素已失效
- 尝试2: click_xy (720,480) → 失败:未命中
→ 必须换一种没试过的方式（滚动找元素/视觉定位/换入口/读页面确认）
```



1. **禁止第三次完全相同**：同一签名同一动作方式失败 2 次后，第三次直接在执行前拦截并注入「该方式已证明无效」提示（不浪费一步模型调用）。

2. **loop 诊断改造**：同签名失败 2 次 → 先触发 W8 重规划 / 视觉兜底 / 语义提示组合拳；3 次才升级人工（现行阈值顺延）。

**涉及文件**：`runner.ts`（tried 登记 + 反思段）、`prompts.ts`（# 反思 区块）、`diagnose.ts`（loop 阈值）。

**验收**：telemetry 中「同一目标重复失败」占比下降 ≥50%；loop 类升级人工的触发频次下降。

**工作量**：2 人日。

### W8 动态重规划（对应参考方案 4.1「跑偏时对照清单发现偏差并重规划」）

**现状与差距**：`buildPlan` 一次性（`planAttempted` 门卫，`runner.ts:1406`）；节点复核失败路径 = 同节点自愈重试 → 2\~3 次后升级人工。缺「带着失败上下文重排剩余节点」。

**设计**：



1. 触发条件（满足其一）：节点连续复核失败 2 次 /done 被拦下且模型声称「页面与预期不符」/ 步数消耗过半但节点进度 <1/2；

2. 重规划输入：原任务 + **已完成节点清单 + 当前失败节点 + 失败原因 + 当前页面状态摘要**，调 PLAN\_SYSTEM\_PROMPT 变体（新增「重规划」说明段）生成**剩余节点链**，整体替换 planIdx 之后的节点（已完成节点不动，时间线提示「已重规划：剩余 N 个节点」）；

3. 每任务重规划上限 2 次，超限走现行人工升级；

4. 重规划调用优先走 W9 的 planner 模型（若已配置）。

**涉及文件**：`plan.ts`（重规划 prompt 变体）、`runner.ts`（触发点 + 替换逻辑）、UI（时间线节点条刷新）。

**验收**：构造场景 —— 任务执行到一半人工改动页面（如提前点了登录），AI 重规划后仍能完成最终目标；现有正常任务节点链行为不变。

**工作量**：2 人日。

### W9 模型分级扩展（对应参考方案 4.3 Model Cascade）

**现状与差距**：本地 0.5B + 云端单模型两级已有；但规划、执行、复核共用云端同一模型 —— 用旗舰模型跑每步执行太贵，用便宜模型做规划又不够强，用户无法分开配。

**设计**：



1. Settings 新增可选 `planner` 块（provider/baseURL/apiKey/model，缺省 = 跟随主配置零影响）：承担 **buildPlan / 重规划（W8）/strict 复核 L2 / 任务增强（✨）/fill\_form 规划**；

2. 失败升级链显式化：本地直出 → 主模型 → planner 模型（当 planner 配置了更强模型时，连续 2 步失败后该任务后续步骤自动切 planner 执行，时间线标注「已升级至规划模型」）；

3. 设置页「高级」折叠区 + 预设快捷填（如主 = deepseek-chat / 规划 = deepseek-reasoner）。

**涉及文件**：`settings.ts`/`types.ts`/`SettingsModal.tsx`、`runner.ts`（双 provider 创建与升级逻辑）、`verify.ts`（L2 用 planner provider）。

**验收**：不配置 planner 时全链路行为与现在逐字节一致；配置后规划 / 复核调用走 planner（token 统计分列显示）。

**工作量**：2\~3 人日。

### W10 动作后轻量核验（对应参考方案支柱 6「没报错≠成功」的动作级落地）

**现状与差距**：page\_changed 诊断只在**失败后**对比 prevExtract；动作成功时模型得到的反馈只有「点击 (x,y)」这类坐标串 ——**点了个被遮挡的死按钮也显示成功**，模型只能靠下一步元素列表自己发现异常（经常发现不了，然后连续脑补）。参考方案：「点了没反应也不报错→校验可见性与可点击性」。

**设计**：



* executeBatch 末尾计算**页面 delta**（与批前快照对比）：URL 变化 / 标题变化 / 候选数显著变化（±30% 以上）/ 滚动位置变化 / DOM 稳定探针的 mutation 计数；

* click 类动作后 delta 全零 → lastResults 注入：「动作成功执行但页面无任何变化（目标可能被遮挡 / 是装饰元素 / 需先触发前置条件），请核对本步目标」；

* delta 摘要正常也注入（一行：「本批后：URL 未变、出现新元素 12 个、弹层已关闭」）—— 给模型确定性的正反馈，替代脑补。

* 成本：零额外 LLM 调用、零额外 CDP 往返（对比现有两个快照即可）。

**涉及文件**：`runner.ts`（delta 计算 + 注入）、`extractor.ts`（无需改，用现有快照）。

**验收**：构造「点击被遮罩挡住的按钮」用例，模型下一步能立即发现并采取补救（现在会继续脑补 2\~3 步）。

**工作量**：1.5 人日。

## 七、P3 评估体系飞轮

### W11 任务回归集（对应参考方案 4.6「自建回归集比选框架更重要」）

**现状与差距**：selftest 是技术自检（CDP / 提取 / UI），不是「任务成功率」度量；telemetry 埋点分类齐全但没有聚合出口。参考方案：从真实业务挑 20\~50 个高频任务，改 prompt / 换模型 / 升级依赖后全量跑，按失败类型分类治理。

**设计**：



1. **用例格式**：复用 testcase 基础设施，新增「任务型用例」—— 自然语言任务（走普通 Agent 循环）+ 末尾验收断言（走 expect 体系）：



```
# 回归任务：聚水潭读今日订单数并填入淘宝搜索
## 任务
（自然语言任务描述，走正常节点链/复核/自愈全链路）
## 验收
- [text] 搜索框值为从订单页读到的数字
- [ai] 时间线最终结果包含订单数
```



1. **执行器**：`npm run regression [-- suite=core]`—— 顺序跑用例（页签隔离、组间冷却、登录态人工预热一次），每例记录：成功 / 失败、步数、token、耗时、失败分类（复用 diagnose 七类 + telemetry failure 埋点）；

2. **报告**：输出 `out/regression-report.md`：成功率、对比上次运行的 delta、失败分类分布、最慢步骤 top5；

3. **用例分层**：core 套件（本地 testpage + 公开站点，10 个，可无人值守跑）/full 套件（含登录态商业站点，20\~50 个，按需跑）。

4. 本地 testpage 扩充 fixture：含 shadow DOM 表单、遮罩遮挡按钮、同名重复元素、iframe 嵌套、受控组件输入（React）——W1/W4/W5/W10 的验收页一并提供。

**涉及文件**：新建 `src/main/regression/`（runner 与报告）、`scripts/run-regression.mjs`、`resources/testpage*.html` 扩充。

**验收**：跑通 core 套件并出报告；本方案全部工作项的验收数字从这份报告出。

**工作量**：3 人日。

### W12 失败分类看板

**设计**：`scripts/analyze-traces.mjs` 聚合 `userData/traces/*.jsonl` → 周报 markdown：任务成功率趋势、失败类型分布（定位 / 等待 / 语义 / 验证码 / 页面改版 / 模型误判）、token 与步数分布、本地直出占比。配合 W11 形成「改动 → 回归 → 周报」闭环。

**工作量**：1.5 人日。

## 十、风险与回滚策略



| 风险                               | 影响         | 缓解                                                                   |
| -------------------------------- | ---------- | -------------------------------------------------------------------- |
| 智能等待在特殊页面误判（mutation 持续动画页面永不静默） | 卡到 8s 上限变慢 | 探针只统计「结构性 mutation」（子节点 / 属性），忽略纯样式 / 动画；超时兜底返回；慢速模式完全 bypass        |
| 网络捕获常开带来内存 / 性能开销                | 主进程内存上涨    | 环形缓冲 50 条 + 仅存 URL/status/ 时间戳，响应体按需拉取且 5 分钟过期                       |
| AX 融合升级改变元素列表行文 → 模型行为回归         | 成功率波动      | state 渲染为增量后缀（编号 / 文案格式不变）；W11 回归集前后对比；`locatorChain`/`axTree` 开关可回退 |
| 定位链 ②③ 唯一性误匹配                    | 点错元素       | ②③ 只在「唯一匹配」才启用，多匹配一律走中心点最近 + W10 核验兜底；telemetry 记录每级命中率便于调权          |
| 重规划生成劣质计划                        | 任务跑偏更远     | 上限 2 次、只替换未完成节点、时间线明示；`replan` 开关一键关                                 |
| 双模型配置增加用户心智                      | 设置复杂度      | 折叠在「高级」区，不配置 = 现状                                                    |
| 截图降清影响时间线体验                      | 观感         | 点击放大时可按需补拍高清？不可行（页面已变）—— 改为「出错步 / 完成步高清 + 常规步缩略」，并在设置留 all 档         |
